## Reproduce and interpret

```sh
python3 -I -S -B tools/profile_report.py all
python3 -I -S -B tools/profile_report.py muse_decode_layer --serving
python3 -I -S -B tools/profile_report.py all --json
python3 -B -m sim --offline
python3 -B -m sim.serving
python3 -B -m sim.calibrate
```

The report tool is host Python with stdlib dependencies only, including the local `sim` modules. It performs no network or GPU work. Full saved per-kernel diffs, including each retained kernel row, are in [all loads](../../prof/report.md) and [serving loads](../../prof/report_serving.md); [JSON](../../prof/report.json) retains shape-level inputs. The selection is automatic on each invocation. Regeneration helpers are under `prof/`; generated caches and outputs are ignored there.

- **H200 measured / judge**: `result.records` benchmark `median_ns`, `baseline_ns`, load weights. Speedup uses the paired baseline in the same receipt, rather than dividing two independent profile totals.
- **H200 measured / profile**: GPU kernel durations, rounded to 0.1 us in the saved report; their sum can include overlapping PDL waits. A profile sum is neither a paired graph median nor exclusive critical-path time. “GPU busy” is retained separately.
- **MODEL**: bytes / 4.32 TB/s and BF16 math / 741.75 TFLOP/s from `sim.hw`, plus the design’s launch costs for total practical time. `% of bound` means 100 × modeled work time / measured profile time, **not** time divided by the bound. Practical rates are design targets, not rigorous lower bounds.
- **STATIC sm_90a**: compiled locally, never executed on H200. **LOCAL sm_120**: independent local timing evidence; no conversion to H200 speed.

The judge saves only its top kernel rows and an “N more” count. Missing names and work attribution cannot be recovered from these artifacts. The tool preserves their time as `unattributed`, and emits `n/a` plus `unexplained` instead of manufacturing a per-kernel bound. Multiple cuBLAS shapes sharing a truncated name get a component bound once, not an arbitrary time-proportional allocation. This is the limit on the requested “each kernel” accounting. For identifiable fused MoE/attention/projection kernels the tool does provide individual efficiency and class. The classes are hypotheses: memory near SOL at ≥70% of the practical work bound, compute at ≥50% when math dominates, latency/launch when the small modeled memory work cannot fill a few us per call; otherwise unexplained. Efficiency >115% signals model/profile disagreement.

## Static Hopper code audit

No H200 execution was attempted. CUDA 13.0 `nvcc -cubin -arch=sm_90a -O3 -std=c++20 --expt-relaxed-constexpr -lineinfo -Xptxas=-v` compiled copies of the **unchanged device functions**, explicitly instantiating the templates; only torch host wrappers were removed. [Extractor](../../prof/compile_static.py), [source hashes](../../prof/sass/manifest.json), [MoE compiler log](../../prof/sass/moe.compile.log), [attention compiler log](../../prof/sass/attention.compile.log), [projection compiler log](../../prof/sass/proj.compile.log). `cuobjdump` supplies resources/SASS and `nvdisasm --print-line-info` supplies source-correlated MoE SASS. MoE uses the TMA-engine one-dimensional bulk-copy instruction (`UBLKCP.S.G`), rather than a multidimensional tensor-map load. These match source templates, not a byte-identical recovered judge cubin.

Decode’s Triton kernels were compiled inside `tools/img` with Triton 3.8, `GPUTarget(cuda,90,32)` emitting `.target sm_90a`, PDL enabled, aligned CUDA pointers/strides specialized as the real JIT does, and reachable token/split/chunk/warp choices. Generic unaligned compilation produces scalar loads and would give a false diagnosis, so those outputs were replaced. [Driver](../../prof/sass/compile_decode.py), [metadata](../../prof/sass/decode_compile.json), per-kernel `.ptxas.log` and `.sass.txt` under `prof/sass/`. Reassembling the PTX with ptxas confirms registers/spills. FA3 and Marlin library cubins are not rebuilt here; their role is measured in the H200 profiles.

Shared sizes above describe source/metadata dynamic allocations, not just cuobjdump’s ABI/static allocation (which includes reserved bytes). MoE’s runtime chooses stages from the device limit; v4 five-stage sizes make a second CTA infeasible even though its register count alone can suggest otherwise. v6’s unused NT2 template compiles with 736/556 spill bytes, but it is never dispatched: reporting that as its hot path would be wrong. QK/attention stack frames have zero ptxas register spills; `LDL`/`STL` alone are not proof of spilling.

**Dequant per weight (STATIC):** v4 `dq8` maps 16 NVFP4 codes to eight BF16 pairs using 7 funnel shifts + 9 logic instructions (one merge plus eight masks), followed by 8 BF16x2 scale multiplies: **24/16 = 1.5 instructions per weight**, excluding loads, scale construction, address math and tensor instructions. The compiled body has 112 `SHF.R.W.U32` and 128 `HMUL2.BF16_V2` sites, consistent with 16 unrolled dq8 instances ×16 weights and 128 pair multiplies. This is not a dynamically weighted issue count. Projection and decode dense kernels have no weight dequant. Attention has FP8 conversion, not NVFP4 weight dequant; decode layer’s expert dequant lives in Marlin and is not statically attributed from these copies.

**Potential stalls (hypotheses):** MoE’s producer `SYNCS.PHASECHK` waits, global phase counters and runtime integer divisions in `decode_unit`; attention’s cluster finalization, softmax shuffle chains (verify has 324 butterfly-shuffle sites versus decode’s 100) and high live-register state; projection’s shared/cluster reductions and low row-CTA counts; decode’s split-K consumers, PDL wait and route top8 reductions. Presence establishes synchronization/instruction dependencies. Without Hopper execution counters it does not establish wait cycles, occupancy achieved, issue utilization or HBM saturation.

## What is not determined

No H200 counters: achieved HBM/L2 bandwidth or hit rate; memory transaction efficiency for page1 gathers; tensor/integer issue utilization; actual occupancy/eligible warps; spill traffic cost; barrier/scoreboard wait cycles; producer/consumer imbalance; cache eviction and true PDL overlap. Static SASS cannot supply those. H200 traces or richer retained profiles are also needed for omitted kernel names and exclusive GPU critical path; counters alone do not restore truncated names. Full-node serving is additionally required for all-reduce/multicast, CPU/scheduler, prefill interference, acceptance/tau and the hidden workload/score curve. There is no measured serving score in this report.

Verified here: stdlib-only execution over all five problems and serving-only filters; exact selection from receipts; profile row accounting including omitted mass; model reruns; public upstream file equality; sm90a compile success/resources/SASS for the requested kernels and the new MoE best. Not verified: Hopper execution of these local cubins, current kernel integration, new port correctness/performance, or node throughput. The reports preserve the distinction between what was observed and what was modeled.
