Serves: G2, G3. Read when a kernel is near an H200 bandwidth, tensor-issue, cache, or register limit.

# Hopper low-level design laws

H200-specific measurements and candidate profiles belong in [FINDINGS](../FINDINGS.md); hardware specifications and primary sources belong in [hardware](hardware.md). The judge replays graph-captured kernels after a cold-L2 read, so a microbenchmark's warm-cache or stream-launch result is not a scored-kernel result.

## Memory requests and cache policy

H200's 4.8 TB/s specification and the judge's achieved bandwidth are recorded in [hardware](hardware.md) and [FINDINGS](../FINDINGS.md). A 128-bit global load controls request width; it does not by itself create enough memory-level parallelism. Coalesced, aligned rows, several independent addresses per thread, and enough resident CTAs are the durable starting point for BF16 GEMV and one-pass weights. TMA is not a default replacement for a streaming 1D load: its benefit comes when a block reuses a tile. The H800/Hopper microbenchmark reports vectorized global reads near 90–91% of theoretical bandwidth and a TMA advantage mainly for large matrices, with little difference for small n: [Hopper study](https://arxiv.org/abs/2501.12084), [Hopper tuning guide](https://docs.nvidia.com/cuda/hopper-tuning-guide/index.html), [earlier Hopper study](https://arxiv.org/abs/2402.13499).

PTX cache controls (`L1::no_allocate`, `L1/L2::evict_first/last`, 64/128/256-byte prefetch-size hints, `createpolicy`, and `prefetch.global.L2`) are hints and may be ignored: [PTX loads and prefetch](https://docs.nvidia.com/cuda/parallel-thread-execution/). Use no-allocate/streaming policy for one-pass dense or expert weights only when it protects reusable inputs; use bounded L2 reuse for a tile read by several tokens. A cold-L2 scored replay cannot justify a whole-bank persistence policy. H800's dual-partition near/far behavior is a locality model, not an H200 bank map: [partitioned L2 study](https://arxiv.org/abs/2501.12084). CUDA's access-policy window is probabilistic and runtime-controlled: [L2 cache control](https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/l2-cache-control.html).

## TMA, WGMMA, and pipelines

TMA moves 1D–5D global/shared tiles without per-thread register staging. A reusable grouped-MoE or prefill tile can use a producer warpgroup, a ring of TMA copies, `mbarrier`, consumer WGMMA, and `wgmma.commit_group/wait_group`. `setmaxnreg.dec/inc` can give producer and consumer warpgroups different register budgets; every warp in the group must execute the instruction and the count follows PTX alignment rules. For a one-pass skinny GEMV, barrier and descriptor overhead can dominate. Sources: [Hopper tuning guide](https://docs.nvidia.com/cuda/hopper-tuning-guide/index.html), [Hopper architecture](https://developer.nvidia.com/blog/nvidia-hopper-architecture-in-depth/), [PTX bulk prefetch](https://docs.nvidia.com/cuda/parallel-thread-execution/), and [CUTLASS Hopper CuTe tutorials](https://github.com/NVIDIA/cutlass/tree/main/examples/cute/tutorial/hopper).

`wgmma.mma_async` is an sm_90a warpgroup operation. RS supplies A from registers and B from shared memory; SS supplies both operands from shared memory. H800 dense microbenchmarks show the shape trend: WGMMA is near peak at N≥64 and smaller N is more sensitive to RS/SS choice, but those are H800 FP16 instruction measurements, not Muse NVFP4 H200 results: [PTX WGMMA](https://docs.nvidia.com/cuda/parallel-thread-execution/), [Hopper microbenchmarks](https://arxiv.org/abs/2501.12084). Choosing RS is a layout/resource decision: it can remove a shared-memory round trip while increasing live registers and reducing occupancy.

## Paged attention and launch dependencies

With page size 1, each logical cache page is one token row. Coalesce a complete aligned K/V row segment and reuse the row across query heads sharing a KV head. Do not infer physical page size, TLB reach, or bank mapping from the logical page table; CUDA documents large physical allocation preferences but not H200 TLB reach: [CUDA physical pages](https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/unified-memory.html). Test address permutations rather than assuming a virtual layout.

CUDA Graphs amortize host submission, and the judge's fixed replay cost is a measurement owned by [FINDINGS](../FINDINGS.md). Programmatic Dependent Launch can start a consumer before producer exit, but overlap is not guaranteed and the consumer must execute `griddepcontrol.wait` before reading dependent data: [CUDA PDL](https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/programmatic-dependent-launch.html), [PTX](https://docs.nvidia.com/cuda/parallel-thread-execution/). PDL can hide independent setup or prefetch; it cannot make dependent data available early. Persistent grids and clusters are useful only when their residency and shared-tile assumptions hold; a resident grid that monopolizes SMs can block dependent work, and no public H200 cluster launch cost was found.

## Format, registers, and binary inspection

Hopper has packed E4M3/E5M2 conversion for FP8 paths, including `cvt.rn.f16x2.e4m3x2`; the query-rounding contract permits E4M3. PTX targets E2M1 conversion to Blackwell-family architectures, not sm_90, and Hopper WGMMA has no INT4 mode. NVFP4 on H200 therefore uses integer bit logic or LUT/`prmt` reconstruction plus BF16 multiply and E4M3 scales. Exact LOP3/PRMT issue cost on H200 is unverified. Sources: [PTX conversion](https://docs.nvidia.com/cuda/parallel-thread-execution/) and the Hopper SASS study ([paper](https://arxiv.org/abs/2501.12084)).

Hopper has a 64K 32-bit-register file per SM and up to 255 registers per thread. Inspect ptxas resource output and SASS for spills, `LDG`/`LDGSTS` or TMA loads, GMMA/HMMA, LOP3/PRMT, barriers, waits, dependency chains and instruction size. `-maxrregcount`, `-dlcm`, `-O3`, and `--allow-expensive-optimizations` are experiments, not performance guarantees: [Hopper tuning guide](https://docs.nvidia.com/cuda/hopper-tuning-guide/index.html), [setmaxnreg PTX](https://docs.nvidia.com/cuda/parallel-thread-execution/), [nvcc guide](https://docs.nvidia.com/cuda/cuda-compiler-driver-nvcc/index.html).

Build Hopper-specific WGMMA/TMA as `sm_90a`; architecture-specific code is not portable across architectures: [Hopper compatibility guide](https://docs.nvidia.com/cuda/hopper-compatibility-guide/). `cuobjdump -sass` and `nvdisasm` are the supported binary inspection tools: [CUDA Binary Utilities](https://docs.nvidia.com/cuda/cuda-binary-utilities/). CuAssembler is unofficial and was not validated for sm_90a; it is not evidence of a legal or reproducible submission.

## Unresolved hardware facts

No primary source checked here establishes H200 bank mapping, exact TLB reach, H200 L2 near/far latency, Hopper PDL savings in Muse shapes, cluster launch latency, or H200 LOP3/PRMT throughput. Treat those as hypotheses until a judge receipt or primary measurement supplies evidence.
