## Workload, evidence, and interpretation

The exact local expert GEMMs are W13 `[32,8192,4096]` and W2 `[32,4096,4096]` before packing; both input and intermediate activations are BF16. The layer's outer hidden width is 8192; its pooled expert width and expert intermediate width are **both 4096**. There are 256 global experts, top-8 routing, 32 local experts under EP8. Do not tune as if all `8*T` routes were local. That is a safe workspace capacity, not expected useful work. Popularity is skewed, and the problem chooses the busiest rank.

**Norm ordering is an architectural constraint.** Muse computes each expert's down projection, multiplies by the zero-centered norm parameter's effective `1+w`, performs RMS normalization across all 4096 coordinates, then multiplies by the routing weight and sums experts. Applying the routing weight before normalization changes its effect; normalizing the sum changes the model. Split-K partial down outputs must first be summed, because their squared norms lack cross terms. W13 must also finish its K reduction before SwiGLU. Keep BF16 materialization points required by SGLang and FP32 global scales/accumulation.

## 1. Humming indexed/grouped GEMM and measured dispatch

**Structure and code.** Humming separates format, GEMM type, and tuning configuration. Its installed ModelOpt schema explicitly supports group-16 E4M3 weight scales and an FP32 per-expert tensor scale. Indexed GEMMs gather routed tokens; grouped GEMMs consume contiguous expert segments. The source provides MMA and WGMMA schedules, optional TMA/warp specialization, and Stream-K. Live revision **`db930afa2256cba49b3e46c0589323c3e80b0bfb`** adds more elaborate SM90 policies than installed 0.1.12: inspect [`humming/tune/sm90.py`](https://github.com/vllm-project/humming/blob/db930afa2256cba49b3e46c0589323c3e80b0bfb/humming/tune/sm90.py), `sm90_policies.py`, `schema/modelopt.py`, and `include/humming/kernel/{humming.cuh,humming_ws.cuh}`. Those live policies include compact MoE schedules, stage/resource constraints, and separate MMA/TMA decisions. Their existence does not establish their performance on Muse.

**Published numbers.** The [authors' announcement](https://vllm-project.github.io/2026/10/19/humming.html) reports approximately 2× Marlin for several medium/large **MXFP4** W4A16 MoE cases on H200. Its 14–43% end-to-end gain is **H20 W4A8**, ineligible here. Do not transpose either claim into “NVFP4 Muse H200 is 2× faster.”

## 2. Quack RS-WGMMA, adaptive expert tiles, and split-K policy

**Exact primitive, already installed.** Quack's [`quack/gemm_w4.py`](https://github.com/Dao-AILab/quack/blob/77a750c0d9548d4a6e23c0f64062d61b3ea420ff/quack/gemm_w4.py), [`blockscaled/nvfp4_utils.py`](https://github.com/Dao-AILab/quack/blob/77a750c0d9548d4a6e23c0f64062d61b3ea420ff/quack/blockscaled/nvfp4_utils.py), and `operand_transform/formats/__init__.py`, live commit **`77a750c0d9548d4a6e23c0f64062d61b3ea420ff`**, implement packed E2M1 + group-16 E4M3 → BF16 register-A WGMMA. The weight/scales are repacked into per-thread A-fragment order, activations are the shared-memory B operand, and global scale belongs in an FP32 epilogue. Installed version 0.6.5 includes this path; an import was verified, execution on Hopper was not.

There is no rounding loss in the finite **E2M1×E4M3 product before the global scale**: two and four significant bits need at most six, within BF16's eight and exponent range. This supports exact in-kernel conversion, not storing a permanent BF16 bank. Keep the FP32 global factor outside the BF16 product.

**What is actually new for us.** Native v4/v6 already put weights on MMA M and tokens on N. Transposing operands alone is not a new optimization. The proposed change is m64/m128 RS-WGMMA, token-N selected per expert, wider vector loads and scale strips, and a pipeline that overlaps conversion with outstanding WGMMA. Native prefill `dev/moe_w4a16.cu` already implements the register-LUT layout; it should be improved, not rebuilt from the Machete article.

For T=128/256, narrow token tiles repeatedly load/decode a hot expert's weights. Some bytes hit L2 under our current ordering, so do not count every reload as HBM traffic. Conversion, shared/register traffic and MMA issue still repeat. Count `n_e` on device and bucket experts into token widths 8/16/32/64, with wider prefill widths where occupancy permits. Fixed launches can read GPU-built task lists; no host copy or value-dependent allocation is necessary.

The 2026 [DA-MoE paper](https://arxiv.org/html/2607.23099v1#S5) independently supports distribution-aware tactics: **B200**, token counts 32–512, 1.16×/1.29× geomean fused-MoE speedups on DeepSeek-V3/Kimi K2. Its full dispatch costs about 14 µs, including roughly 8 µs conditional-graph branching. This is not an H200 result, and that dispatch overhead is unattractive for our smallest loads. Copy the histogram-to-tile idea into a fixed graph/device scheduler; do not assume its conditional graph wrapper composes with the judge's outer capture. No public DA-MoE implementation was verified from the paper.

**Split-K versus Stream-K.** Pool work across **all active local experts** first. With 64 weight rows/tile, W13 already has 128 row tiles per expert and W2 has 64; two active experts often supply enough independent output tiles. Inter-CTA split-K then adds partial-output traffic, locks/reduction, and delays SwiGLU or RMS norm. Split only when total useful output tiles or the final scheduling wave underfill the 132-SM GPU. Stream-K can repair tails, but is not intrinsically beneficial at every expert count. The installed Humming default enables it broadly; existing `cand_humming8.py` is the relevant off-control. Quack's dense starvation heuristic must be recomputed over the **grouped** grid rather than applied separately to each expert.

No published H100/H200 NVFP4 grouped result or BF16-peak percentage was found for Quack's path. Estimate 1.15–1.50× over native v6 at large verify only if a controlled H200 profile confirms the repeated-decode/padding diagnosis. A fixed 128-token tile for every expert is contradicted by Humming4's receipt.

## 3. Layer fusion and PDL chains

**Structure.** Fuse reductions with their immediate consumers: post-attention norm + FP32 residual gate + pre-FFN norm; pooled-input norm + top-8 route processing; post-expert norm + weighted sum; post-FFN norm + residual + next-input norm. A PDL consumer can initialize barriers and fetch immutable weights before waiting for the producer's data. It must wait before reading dependent activations; every producer CTA must participate correctly in the release protocol. Opportunistic overlap cannot be required for forward progress. NVIDIA documents Hopper support and graph capture in the [CUDA PDL guide](https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/programmatic-dependent-launch.html).

**New primary H100 evidence beyond the setup survey.** The [PDL reconstruction](https://github.com/tie-pilot-qxw/pdl-megakernel-reconstruction/blob/8664720072fefb62cc3a097c9c5bba8c936294c5/docs/reconstructing-a-megakernel-with-pdl.md), commit **`8664720072fefb62cc3a097c9c5bba8c936294c5`**, reuses Hazy's BF16 operators in an 81-kernel Llama-3.2-1B chain. Matched in-process decode-step results: persistent 983.127 µs, PDL 1009.711 µs, normal dependencies 1169.071 µs. Thus PDL recovers 97.4% of persistent throughput. Its SGLang bar uses a different server timing scope and is not a strict comparison. Source: `demos/low-latency-llama/matvec_pipeline.cuh`; harness: `experiments/pdl-reconstruction/harness/bench_direct_tk_pdl_ablation.py`. This is an author-reported reproduction, not independently rerun here.

The [SGLang low-latency post](https://www.lmsys.org/blog/2026-10-18-sglang-low-latency-mode) supplies a relevant speculative-verification example, but on **4×GB300 with six rows/request**, not Hopper/Muse: profiled layer 96.8→68.4 µs while graph kernel count barely changes. It attributes gains to early PDL release, GEMM-epilogue peer publication, and bitmap routing at ≤8 rows. No H100/H200 number is given there.

**Our implementation boundary.** Layer v3 already has `PDL=True`, `_pdl_start`, `_pdl_wait`, `_boundary_kernel`, `_route_norm_kernel`, and `_post_expert_kernel`. Enabling a flag or claiming all baseline glue again would repeat completed work. `cand_v0t` also already showed that one aggressive path can regress. The next controlled experiment is an **early-release placement / actual next-weight-load** comparison using identical GEMMs. An L2 prefetch instruction is not equivalent to keeping the next operator's TMA-loaded tiles resident.

The router and pooler share the normalized layer input and can overlap, or share an input scan as v3's concatenated pooler/router-hi/router-lo GEMM does. Use both BF16 router halves with FP32 accumulation; changing it to one BF16 copy is disallowed. Keep FP32 residuals and BF16 activation rounding points. Estimate another 5–20 µs at verify 1 only if a trace shows remaining gaps; at ~190 µs this is about 1.03–1.12×. No cited PDL work proves a gain for B=16/32, q_len=8.

## 4. Timed expansion plus DeepGEMM grouped BF16 prefill

**Structure/code.** Expand the touched packed experts to exact BF16 **inside each timed call**, excluding FP32 global scales; run contiguous grouped BF16 GEMMs, apply global scales in FP32, SwiGLU, and Muse's finalization. DeepGEMM fixes N/K across groups while device metadata describes variable M segments. Source revision **`5081f8513af57e61696de4f4f04b0e707ffb503e`**: [`impls/sm90_bf16_gemm.cuh`](https://github.com/deepseek-ai/DeepGEMM/blob/5081f8513af57e61696de4f4f04b0e707ffb503e/deep_gemm/include/deep_gemm/impls/sm90_bf16_gemm.cuh), `scheduler/gemm.cuh`, `tests/test_bf16.py`. The image has the Muse fork **0.2.1.post1+muse.cbe1727**; both `m_grouped_bf16_gemm_nt_contiguous` and `_masked` were verified as present.

**H200 evidence:** `runs/muse_prefill_layer/20261023T081413Z_check_300425fdfc3e4aed.json` gives prefill v1 1.228× overall, load ratios **1.020 / 1.178 / 1.543×** for turn-1 / turn-4 / first-turn. Native RS-WGMMA v3, receipt `82a4e50b54294a2a`, gives **1.345× overall**, **1.212 / 1.369 / 1.468×**. Thus integrated dequant already wins the smaller prefill loads, while the simple expanded-BF16 approach remains a serious first-turn control. The first-turn ratio advantage is `1.543/1.468≈1.051`; it is not a measured composed dispatch and the runs have different baselines.

**Cost and fit.** One local expert contains 50,331,648 weights: 28.31 MB packed including group scales versus 100.66 MB BF16. Expanding all 32 local experts creates **3.22 GB** of BF16 scratch; the write plus later read is **6.44 GB**, a 1.34 ms lower bound at 4.8 TB/s, before packed reads, activations and kernels. These are derived byte counts, not H200 timings. This is tolerable only when sufficient useful GEMM work amortizes it. Recompute live ranges every replay; never retain expanded values across calls. Shape-based capacity allocation is capturable, value-based allocation is not.

The present v1/v2 code already follows timed expansion. Improvements to test: expand only experts with live routes using a fixed launch, avoid unnecessarily zeroing full capacity, use padded starts plus live ends correctly, and reduce peak workspace by expert chunks when the extra launches do not cost more than they save. A serving port must price scratch against KV capacity and collectives. Report GEMM-only and full-call times separately.

**Achieved fraction of BF16 peak: evidence boundary.** No checked primary source reports the exact NVFP4 group-16, BF16-activation, SM90 grouped path at a measured percentage of BF16 peak. DeepGEMM's famous **1550 TFLOP/s H800** README result is FP8 and cannot be normalized as a BF16 accomplishment. As a nearby *dense INT4/FP16* comparator, the [Humming raw H200 JSON](https://github.com/vllm-project/humming/blob/db930afa2256cba49b3e46c0589323c3e80b0bfb/benchmarks/results/h200/dense_n8192_k8192_g0/humming_w4a16_int4_float16.json) provides the following; these percentages are **our calculation against nominal 989 TFLOP/s**, not author-reported NVFP4 results:

| Dense N=K=8192 | Time from source | Effective TFLOP/s | Fraction of nominal BF16/FP16 peak |
|---|---:|---:|---:|
| M=256 | 58.815 µs | 584.20 | 59.1% |
| M=1024 | 201.124 µs | 683.35 | 69.1% |
| M=4096 | 801.593 µs | 685.83 | 69.3% |

The source uses per-channel INT4 scales and FP16 activations, not NVFP4's group-16 scales, and reports a device compute rate around 848 TFLOP/s. Neither the survey nor the ceiling model establishes that 75% is attainable here.

## 5. MonoMoE persistent streaming, adapted to Muse

The [paper, arXiv:2609.04244v1](https://arxiv.org/html/2609.04244v1), places the **entire 1–8-token decode tile** on MMA N and parallelizes across weight-row tiles. Persistent CTAs fuse routing, both projections, activation, quantization, and reduction; readiness flags connect projection schedules and prefetch warps hide epilogues behind the next expert. Its H200 complete-operator gains are up to **1.54× over tuned vLLM Triton grouped GEMM**, with 1.02–1.17× remaining at B=8 across the tested models. Expert GEMM operands are FP8; these numbers do not validate NVFP4/BF16. The paper is internally inconsistent about DeepSeek-V3.1 serving: its introduction says TPOT changes from a 1.2% regression to a 3.7% reduction, while §4.4's listed latencies imply 12.8–3.5% reductions. Use its isolated-operator evidence, not that end-to-end claim, for planning.

**Code and image.** FlashInfer live commit **`8ec9464ce81d81c9e3670aa09acd1a8780f83695`**, [`csrc/fused_moe/monomoe/src/moe.cuh`](https://github.com/flashinfer-ai/flashinfer/blob/8ec9464ce81d81c9e3670aa09acd1a8780f83695/csrc/fused_moe/monomoe/src/moe.cuh), plus `moe_routing.cuh`, `moe_up_projection.cuh`, `moe_down_projection.cuh`, `moe_tma.h`, and `flashinfer/fused_moe/monomoe.py`. The corresponding source is bundled in FlashInfer 0.7.0.post1. Model specializations must change: E=32 local, H=I=4096, BF16 input/intermediate, NVFP4 RS conversion, and Muse's norm before weighting. Generic FP8 quantization and its final reduction cannot be reused unchanged.

**Gain hypothesis.** Native v6 already has a persistent kernel, early weight loading, fused SwiGLU, per-expert completion counters and final norm/sum. The useful delta is finer readiness—per expert/token tile rather than unnecessarily broad phase waits—and epilogue work on otherwise idle producer resources. Avoid a full-grid barrier where per-token expert-completion events suffice, but preserve true full-K/full-row dependencies. At T=128/256 do not keep all tokens in every CTA just because B≤8 worked in the paper. Histogram buckets or grouped scheduling are more appropriate. No MonoMoE H200 q_len=8 × 16/32-request result was found.

## 6. Marlin-MoE and newer forks: retain the efficient parts

Modern vLLM source, commit **`ccd4e4030f4b86f959a3cb3435437c0f592c88b1`**, includes [`csrc/quantization/marlin/dequant.h`](https://github.com/vllm-project/vllm/blob/ccd4e4030f4b86f959a3cb3435437c0f592c88b1/csrc/quantization/marlin/dequant.h), `csrc/moe/marlin_moe_wna16/{marlin_template.h,ops.cu}`, and `vllm/model_executor/layers/fused_moe/experts/marlin_moe.py`. SGLang's image contains its JIT variant. The relevant lineage keeps packed weights in fragment-friendly order, overlaps asynchronous loads, and exploits exponent/bit placement to feed BF16 `mma.sync`. Our native implementation already inherits the important decode idea; the original [Marlin paper](https://arxiv.org/abs/2408.11743) is not evidence for Hopper NVFP4 MoE performance.

A source-level correctness lesson is newer than many descriptions: [vLLM PR #34577](https://github.com/vllm-project/vllm/pull/34577), merged 2026-03-17, fixes small-scale BF16 underflow by lossless power-of-two rescaling and global-scale compensation. A simplistic exponent widening assumption was insufficient. Our `_encode_scales` explicitly checks reversible encoding, including E4M3 subnormals; do not replace it with an unchecked bit shift or claim the historical bug affects our checked kernel.

Recent SGLang [NVFP4 fallback PR #19652](https://github.com/sgl-project/sglang/pull/19652) and its [DeepSeek-V4 roadmap](https://github.com/sgl-project/sglang/issues/23602) distinguish Marlin W4A16 from FlashInfer **MXFP4** W4A16. This is format/dispatch support, not evidence of a new fast NVFP4 Hopper grouped architecture. PR #19652's page could not be fetched directly here; the roadmap and installed implementation were checked, so its implementation details are not asserted.

For Muse, narrow tiles and resource use matter more than a new backend name. Existing `cand_marlin2` already fused its glue and reached **1.194× overall** on H200 (`a7d687cf44ff4b12`), below native v6. Keep it as a diagnostic comparison when changing packing, scaling, or routing; expected additional native gain from only copying newer dequant code is small and unmeasured.

## 7. Register LUTs, FLUTE, and TileLang conversion pipelines

There are two concrete exact strategies to compare. Our native `dq8` reconstructs tiny biased BF16 values with rotate/AND instructions after a custom lossless bit repack and compensates with exactly encoded scales. Quack uses the eight E2M1 magnitudes `{0,.5,1,1.5,2,3,4,6}` as low/high-byte register LUTs, `prmt` byte selection, sign assembly, and paired BF16 scale multiplication. Its conversion helpers are in the §2 source; prefill `dev/moe_w4a16.cu:decode8` already contains the LUT strategy. Hopper needs no hardware E2M1 converter for either method.

[FLUTE](https://arxiv.org/abs/2407.10960) contributes offline reshuffling and vectorized/duplicated LUT organization. Code **`9eb83a12d56949bbe7fe9c836ba97a67bd1e3761`**, [`flute/csrc/qgemm_kernel_example.cu`](https://github.com/HanGuo97/flute/blob/9eb83a12d56949bbe7fe9c836ba97a67bd1e3761/flute/csrc/qgemm_kernel_example.cu), is absent from the image. Its reported 2–4× GEMM gains at batch <32 and group size 128 are not H200 NVFP4 group-16 evidence. Retain E2M1's fixed codebook; learned NF4/NFL codebooks or requantization would change the weights.

TileLang live revision **`cb26ee0fafe57a1274050a4a8d0ea6817618613a`** has [`examples/dequantize_gemm/example_dequant_gemm_bf16_fp4_hopper.py`](https://github.com/tile-ai/tilelang/blob/cb26ee0fafe57a1274050a4a8d0ea6817618613a/examples/dequantize_gemm/example_dequant_gemm_bf16_fp4_hopper.py) and `quantize/nvfp4.py`. The example supplies fast bit-twiddled and simple conversion paths and a dequantized shared-memory staging pipeline; its bare FP4 GEMM is not a complete group-16 + FP32-global MoE runner. TileLang 0.1.12 is installed; inclusion of this exact example in the wheel was not established. No matching published H100/H200 throughput was found.

The experiment is an isolated conversion/mainloop comparison with **identical grouping and MMA shape**, inspecting generated instructions, register counts, spills and H200 full-path time. A LUT can reduce arithmetic yet add permutation pressure or register live ranges. Do not predict a large end-to-end gain from instruction count alone. Preserve small/subnormal/zero scales and BF16 materialization semantics.

## 8. Machete and CUTLASS mixed-input grouped GEMM

Machete pre-shuffles packed weights into wide shared-memory register loads and feeds Hopper RS-WGMMA with conversion in registers. The [author's H100 article](https://developers.redhat.com/articles/2024/10/14/introducing-machete-mixed-input-gemm-kernel) reports competitive FP16 performance at batch/prefill sizes ≥128, plus 29%/32% input/output serving-throughput gains on one H100 for GPTQ Llama-3.1-70B at higher request rates. Those are INT4 dense-model comparisons, not NVFP4 MoE or q_len=8 results. The article attributes about 37% lost peak compute to relying only on older MMA; this is not a universal measured 1.59× latency gain.

Code is in vLLM **`ccd4e4030f4b86f959a3cb3435437c0f592c88b1`**, [`csrc/quantization/machete/machete_mainloop.cuh`](https://github.com/vllm-project/vllm/blob/ccd4e4030f4b86f959a3cb3435437c0f592c88b1/csrc/quantization/machete/machete_mainloop.cuh), `machete_prepacked_layout.cuh`, `generate.py`, and `Readme.md`. Machete itself is absent from site-packages.

CUTLASS commit **`91843b71d90737e0a9b86f7d9df213cff5a3526f`**, [`example 55 README`](https://github.com/NVIDIA/cutlass/blob/91843b71d90737e0a9b86f7d9df213cff5a3526f/examples/55_hopper_mixed_dtype_gemm/README.md), [`example 69 README`](https://github.com/NVIDIA/cutlass/blob/91843b71d90737e0a9b86f7d9df213cff5a3526f/examples/69_hopper_mixed_dtype_grouped_gemm/README.md), documents the critical limitations: narrow operands go through registers; scale types are at least two bytes; scaling groups must span the CTA K tile or a multiple; grouped group-wise scaling assumes identical shapes. Our byte E4M3 scales every **16 K elements**, combined with irregular per-expert M, do not fit that stock interface. Merely instantiating `float_e2m1_t` is insufficient. Relevant mainloop headers are vendored inside the image, not verified as prebuilt runnable NVFP4 kernels.

Use the warp-specialized producer/consumer organization and pre-shuffled fragment loads as source material for §2. To avoid repeated K=16 scale updates, load a strip of scales for a wider K tile and apply the appropriate pair to each k16 fragment before WGMMA. Do not widen the scale group or convert the codebook to INT4. High effort relative to adapting the already installed Quack/Humming primitives. No source-backed percentage of BF16 peak for the target NVFP4 grouped case was found.

## 9. Cohere, Hazy “No Bubbles,” and ThunderKittens layer task graphs

**Structure.** Resident workers execute ready GEMM/attention tiles, publish fine-grained completion counters, and fetch immutable next-stage weights while waiting for activations. Cohere is the closest MoE implementation to inspect: commit **`67d0b9ca22ea3652796b715d1d1863459e0e2c3c`**, [`src/decode/megakernel.cuh`](https://github.com/cohere-ai/cohere-megakernel/blob/67d0b9ca22ea3652796b715d1d1863459e0e2c3c/src/decode/megakernel.cuh), `gemm-n8-wgmma.cuh`, `runtime.cu`. Its n8 BF16 WGMMA and dynamic expert task records are useful donors; NVFP4 conversion and Muse norm semantics must be added.

The [Cohere measurements](https://cohere.com/blog/megakernels) are one H100, BF16 North Mini Code, 8K context, vLLM 0.24 FA3/Triton MoE: B=1 **292 vs 185 tok/s (1.58×)**; B=8 **1000 vs 757 (1.32×)**, also recorded in the pinned README. Real-prompt serving at B=8 gives **1.25–1.41×**; prefill uses separate PyTorch kernels. There is no B=16/32 or q_len=8 result. Its model has **parallel attention and MoE**, enabling backfill between independent branches. Muse's expert input depends on attention and residual normalization, so that major source of overlap does not transfer.

[Hazy's “No Bubbles”](https://hazyresearch.stanford.edu/blog/2025-05-27-no-bubbles) evaluates BF16 Llama-3.2-1B, one sequence, 32-token prompt/128 outputs, no speculation: 78% H100 bandwidth and over 1.5× existing systems. It measures about 1.3 µs even for a CUDA-graph dummy-kernel boundary. Code **`7309cec801537b61fea3b50d7dfe454a6cde578e`**, [`include/megakernel.cuh`](https://github.com/HazyResearch/Megakernels/blob/7309cec801537b61fea3b50d7dfe454a6cde578e/include/megakernel.cuh), `include/{loader,consumer,storer}.cuh`, `demos/low-latency-llama/`. This is a different size/context/precision regime; §3's later PDL reproduction weakens the inference that a resident interpreter is required to recover most boundary losses.

ThunderKittens is the underlying tile/pipeline toolbox, not a measured Muse whole-layer solution. Live revision **`67845f5fa48d05343dbbc1ba1403f11061f08d2d`**, [`kernels/gemm/educational_h100`](https://github.com/HazyResearch/ThunderKittens/tree/67845f5fa48d05343dbbc1ba1403f11061f08d2d/kernels/gemm/educational_h100), and `include/` supply Hopper building blocks. None of these implementations or `kittens.cuh` was found under image site-packages. A full port therefore carries compile/integration cost in addition to the new scheduling work.

For a model-sized rewrite, enforce resident-grid resource limits and explicit memory-ordering contracts. A software grid barrier is safe only when its scheduling assumptions hold; adding concurrent serving kernels changes those assumptions. More warps or a larger tile can lower residency enough to negate fusion. This is a late experiment after component improvements, not the first route to serving-priority rank.

## 10. MPK / Mirage

[MPK, arXiv:2512.22219v1](https://arxiv.org/html/2512.22219v1), compiles tensor programs into SM-level tasks and runs decentralized worker/scheduler queues. It supports task pipelining, gather-GEMM, heterogeneous MoE load balancing and in-kernel NVSHMEM. The study uses BF16, 64-token prompts and 1024 output tokens, maximum batch 1–16. Its headline **1.0–1.7×** spans **A100, H100 and B200**, not an H200-specific result. It reports **1.1–1.4×** throughput gains on 8×H100 TP experiments; neither setup tests our eight-token verification blocks. Host request scheduling and page allocation are part of its advantage, while the kernel challenge times a captured GPU forward.

Expected 1.03–1.15× over an already good chain is an inference, not a paper prediction.

## 11. FlashFormer

[FlashFormer v1](https://arxiv.org/html/2505.22758v1) uses a unified cross-operator memory pipeline and fuses GLU: gate/up, SwiGLU and down contributions share a running output vector. On one H100 SXM, BF16 Llama-3.1-8B B=1, its table gives **182 vs vLLM 146 tok/s** at 128-token prefix, **174 vs 108** at 6144 prefix. GPTQ 70B gives **48 vs GPTFast 47**, rising to **45 vs 40** at longer prefix. These results do not include q_len=8, MoE, or SGLang. The setup survey's “8K×8K layer, 62→48 µs” assertion was **not located in this primary v1 paper** and is not used as evidence here.

The old `aninrusimha/flashformer` repository now contains only a migration notice. Current source is **`cheetah-lang/flashformer@4768b7684ddf94d4845e5c36e2370a3f3c5bd112`**, [`src/utils/memory_pipeline.py`](https://github.com/cheetah-lang/flashformer/blob/4768b7684ddf94d4845e5c36e2370a3f3c5bd112/src/utils/memory_pipeline.py), `src/glu/fused_v_glu.py`, and `src/utils/barrier_utils/`. It is absent from the image.

Partial down sums could feed a later full-row norm, preserving BF16 SwiGLU rounding and FP32 accumulation; applying the norm to partials is invalid. The large 4096-wide output vector and multiple verify tokens make register pressure much greater than in its B=1 demonstration. Selective GLU fusion is worth comparing inside §5, but porting the full generator is lower value than Quack/Humming. No Hopper NVFP4 gain is established.

## 12. llama.cpp `mul_mat_id`: MMVQ and MMQ

Live source **`f5027fb21307eb264aed483242603d68c87b0fe3`**, [`ggml/src/ggml-cuda/mmvq.cu`](https://github.com/ggml-org/llama.cpp/blob/f5027fb21307eb264aed483242603d68c87b0fe3/ggml/src/ggml-cuda/mmvq.cu), `mmq.cuh`, `vecdotq.cuh`, and `mmf.cu`, implements indexed expert matrix operations and batch-dependent matvec/matmul dispatch. A scalar/vector-CUDA-core GEMV can be useful at one token, but must beat the native tensor-core implementation with cold L2 on H200 before it earns further effort. ## 15. LiquidGEMM and other 2025–2026 low-bit papers: what to exclude

[LiquidGEMM, arXiv:2509.01229v1](https://arxiv.org/html/2509.01229v1), presents LiquidQuant and an implicit fine-grained load/dequant/MMA pipeline on Hopper, reporting up to **2.90× W4A8 kernel** and **4.94× system** speedups; comparisons to TRT-LLM are 1.12–1.63× at kernel level. ## Hand-offs

The first five are the recommended implementation order. All H200 confirmation below means a future receipt produced through the repository's run wrapper, after local correctness/capture screening; no runs were launched by this lane. Use cold-L2 graph replay and fresh routing, including nearby token counts, zero-local-route and concentrated-expert cases. Preserve full precision and the norm ordering above. Keep an explicit useful-route count when calculating effective throughput.

### A1. Carry the best measured experts into the decode layer

- **Problem/start:** `problems/muse_decode_layer/cand_moe4.py` or the MoE portion of `cand_native_glue.py`; donor arithmetic from `problems/muse_moe_w4a16/cand_v6.py` and `cand_humming3.py`. These layer candidates already exist; first inspect their latest receipts rather than submitting the same integration again.
- **Change:** replace the embedded v4 expert path with v6's occupancy/staging; use the Humming3 configuration for T=256 only as the first controlled dispatch. Map local IDs directly, translate `post_expert_norm` to the donor's raw `post_norm_w`, and return the local BF16 contribution before unpooling. Compile/repack only in `prepare`. Do not duplicate the large packed bank unnecessarily.
- **Expected:** about 1.10–1.30× large-verify layer speed versus layer v3's Marlin experts is an Amdahl hypothesis. The normalized T=256 MoE-only delta between Humming3 and v6 is 1.175×; a six-load native/Humming composite projects only 1.027× incremental MoE geomean.
