# Streaming projections (P7 / G1)

`python3 build.py` emits `../streaming_gemv_lab.py`: a self-contained lab and
`StreamingProjection` drop-in. Source is `kernel.cu`, `runtime.py.inc` and
`lab.py.inc`. It reads the original contiguous BF16 bank; the pool/router bank
is the permitted BF16 pooler + FP32 router hi/lo split. No NVFP4 bank is involved.

M=1 uses 16-byte global loads, with 4/8/16 vectors issued per lane before the
FMAs consume them. A lane-preserving shuffle of the ring hash makes all
weight loads precede the first FMA in actual SASS (bare compiler/barrier
fences did not). M>=8 uses BF16 `mma.sync.m16n8k16`, weight rows on its M side,
and a 2-4 stage `cp.async` ring. Shared rows have an eight-BF16 pad to avoid
fragment-load bank conflicts. Split-K uses disjoint FP32 partials and a last-CTA
reducer in the same launch; no spin, zeroing or reduction launch is timed.

`StreamingProjection(w, m, config, splits, fp32)` is constructed in prepare.
`op(x)` returns its stable `[M,N]` output. Each instance owns its scratch and
must not run concurrently on two streams. The decode boundary adapter is
`return op(x).unsqueeze(0), 1`. Pool/router keeps all 4608 FP32 outputs and the
existing consumer adds the router hi/lo rows. Shape winners require an H200
receipt before integration; a configuration number alone is not a winner.

The lab gates every trial against FP32 accumulation (1e-4), including outliers,
single-column probes, two inputs, per-row bounds, router hi/lo and counter reset.
It flushes 256 MiB before each replay, screens all configurations and pairs the
two finalists with cuBLAS 20 times in alternating order. A plain-read kernel
uses the identical protocol. Both raw and fixed-replay-cost-subtracted TB/s
are reported, so the new measurements can be compared with the old read sweep.
`pass35` uses the subtracted convention; `ratio` is the raw paired ratio.

All decode-layer roles at M=1/8/16/32/128/256 precede the DFlash TP8 roles. The
drafter o role is identical to decode o, and context_kv uses a lossless TN view
of the released NN bank. Large-M tuning remains a GEMM problem, and the first
local screen loses there; it does not authorize a serving or decode change.

Local admission: `CUDA_VISIBLE_DEVICES=0 tools/img python
problems/muse_bf16_proj/dev/streaming/validate.py`. `validation.json` records
537 checked configurations and 135 fresh-input graph tests. sm_120 executes
the same fragments/reducer; configurations exceeding its shared-memory limit
use fewer ring stages (96 KiB dynamic cap). The H200 build retains every stage.
`compile_sm90a.json` records the actual Hopper build: 20 kernels, no spills,
160 registers maximum, with 128-bit loads/async copies and BF16 HMMA in SASS.
Regenerate this evidence with `python3 dev/streaming/audit.py` from the problem
directory; it rejects spilling and a collapsed register-prefetch window.

The unsent next payload `../streaming_gemv_vector_lab.py` is generated by
`build_vector.py` plus `consumer_vector.cu.inc`. It loads 16 bytes from shared
memory per operand row and feeds two MMA steps with the same K permutation.
It changes the shared row pad to 32 BF16s so the two rows in an eight-lane
128-bit transaction use opposite halves of the bank array. Keeping the scalar
path's eight-BF16 pad did not improve local timings despite fewer LDS instructions.
`vector_validation.json` and `vector_compile_sm90a.json` cover the same gates
and native build. It awaits the first lab's H200 evidence; local ranking does
not select a decode dispatch. `read_receipt.py <job>` makes a per-shape handoff
only from a completed local receipt whose payload hash matches the source.

Audit scope: all projection `cand_*.py`, `muse_proj.py`, `muse_prefill_dense.py`,
`muse_prefill_gemm.py`, and `muse_dflash.py`. No prepared BF16/FP8 copy of NVFP4
weights is used by them; the probe candidate's synthetic FP4 decoder is a lab
instruction-throughput test, not a prepared weight bank.
